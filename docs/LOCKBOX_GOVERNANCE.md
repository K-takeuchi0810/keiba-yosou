# 次の世代の新しい窓 (fresh window) の規則 (2026-10-06)

外部の指示者の決定 (2026-10-06): Phase 0.5-5 の族を閉じた後、**A″ の探索や結果を見る前に**、次の世代の候補 (A″・通過順位版の C など)
に共通の新しい窓の規則を先にコミットする。この文書のコミットが、開始日を決める基準の時点になる。

## 1. なぜ今決めるのか

- 2026-09-17 の延期 (`config.SEALED_FROM = None`、`docs/CHARTER_2026_09_17.md`) は「試す価値のある候補が無いのに封印を始めると、一度きりの窓を
  既知の答えの確認に費やす」ためだった。今回の規則では、窓は **蓄積するだけで開かない** (開くのは事前登録した候補の情報量の条件が満ちたとき) ので、
  延期の理由とは衝突しない
- 「候補が完成した日から封印を始める」と、開発の期間中に走ったレースを新しい証拠として使えなくなる。かといって、候補の仕様や結果を見てから
  開始日を決めると、開始日そのものが探索の自由度になる。だから **候補を見る前に、機械的な規則で開始日を固定する**

## 2. 開始日

- **FRESH_FROM = この文書をコミットした日の翌日以降で、最初の JRA の開催日** (中央 10 場、平地・障害を問わない)。
  2026-10-06 時点の見込みは 2026-10-10。開催日は出馬表の取り込みを待たず、**年間の開催スケジュール (JV-Data YS、`schedules` 表、
  2025-12-22 作成) で決める** (`scripts.research_window.determine_fresh_from`。結果の列の無い表だけを読む)。出馬表の取り込み後に `races` の
  鍵の列で確かめるのは任意で、食い違っても値は変えない
  (2026-10-06 追補: 当初は「出馬表の取り込みの後に races で確定」と書いたが、data-pipeline のレビューで、規則の時点で既に存在する
  スケジュールで決めるほうが、10/10 の出馬表・オッズが入る前に境界を閉じられて裁量が減ると分かったので改めた。値は同じ 2026-10-10)。
  開催の中止・順延があっても規則は変えず、最初に確定した対象開催日を境界として保つ。下の 10 に記録する
- 2026-09-14 〜 FRESH_FROM の前日 (以下「間の期間」) は、**新しい窓には入れない**。ただし研究の目的で結果を見ることもしない
  (従来の `CONFIRM_FROM = 20260914` の「未消費」の扱いを保つ)。→ 永久に `RESERVED_UNTOUCHED` (9)
- 窓の終わり (`SEALED_UNTIL` 相当) は **固定の日付にしない**。開封の条件は時間ではなく情報量 (4)

## 3. 窓の性質

- 次の世代の候補 **すべてに共通** の 1 つの窓。候補ごとに別の窓を切らない
- 同じ窓を複数の候補が使う場合、多重比較は **開封の前の事前登録で** 族として宣言する (後から足した候補は、同じ窓では確証にしない)
- 窓を 1 度でも「結果を見る目的で」開けたら、その期間は以後 **新しい OOS と呼ばない** (`config.CONSUMED_WINDOWS` に記録)
- 候補の事前登録が未完成なら、窓は蓄積を続けるだけで開かない。蓄積の間に窓の中を見てよいのは、結果を読まない件数 (対象レースの数・
  件数の見込みの母数) だけ。着順・払戻・勝ち馬・確定オッズを含む列は読まない

## 4. 開封の条件 (候補ごと、事前登録で固定)

- **主検定の開封**: 学習期 2022-2024 で凍結した S を使い、結果を読まない検出力 (§8-7b と同じ手順) から `MDE ≤ β_target` になる
  最小のレース数 `N_primary_required` を事前登録で決める。開封は「窓の対象レース数が `N_primary_required` 以上になった **最初の月末** (JST)」。
  月末の点検は機械的に行い、件数に届いた瞬間に随時開けることはしない
- 2026-10-06 追補 (validation のレビュー、候補を見る前に固定): 次の 3 点を **候補に共通** で固定する
  - **検出力の代わりの年**: `N_primary_required` は、凍結した S を **2024 年** (development の最後の年) の対象の行に当てた、結果を読まない
    Fisher の SE (と学習期のブートストラップの SE を √(レース数の比) で換算した値の大きい方) から、`N = ceil((3.4174 × σ₁ / β_target)²)`
    (σ₁ = 1 レースあたりの SE) で決める。2025 (consumed) や pooled では決めない
  - **件数の単位**: 窓の件数は `count_fresh_races` の **確定 (data_div 7) の平地の JRA レース数** で数える。候補の解析の対象 (除外の後) との
    比 r = (2024 の候補の解析対象のレース数) ÷ (2024 の確定の平地の JRA レース数) を事前登録で固定し、開封の条件は
    `n_confirmed ≥ ceil(N_primary_required / r)`
  - **月末の点検の時刻**: 月 M の点検は、翌月の **8 日 (JST) 以降** に `to = M の末日` で行う (結果の取り込みを待つため)。未確定 (pending) は
    数えない。最初に条件を満たした月 M の末日までを主検定の窓にする
- **金額の試験の成熟 (money-evaluation maturity)** は主検定の開封と **別の状態**: `ratio_buys_at(1, β_target)` の件数の見込みが
  `MIN_BUYS_FOR_MONEY_PASS` (1,500) 以上になる時点を別に事前登録する。主検定に十分なレース数が先に溜まっても、金額の試験はそれまで判定しない
- 開封は候補ごとに 1 回。開封の手順は Phase 0.5-5 の型 (凍結 → 結果を読まない検出力 → 錠のコミット → 開始の印 → 主検定 1 回 → 2 層の解釈)

## 5. 候補ごとに、開封の前にコミットするもの

主検定の仮説 / β_target / 族と多重比較 / S の定義 / 標準化 / 市場の項 (log P_market、§8-6b) / 検出力の手順 / 最小のレース数
(`N_primary_required`) / 金額の試験をするなら最小の購入点数 (1,500) と成熟の条件 / 開封の月末の点検の手順 / 結果の 2 層の解釈の規則

| 状態 | 意味 |

まず 2022-2024 だけで完成させ、検出力と件数の見込みまで評価する。

## 7. コードでの強制 (2026-10-06 追補、外部の指示者の決定)

- **既存の本番の封印 (`config.SEALED_FROM`) は使わない (None のまま)**。入れると既存の関所 (`config.guard_analysis_window`、
  `scripts.backtest.list_races`) が本番と ai-builder に効くため (調査 2026-10-06、`ai-builder/builder/matrix_daily.py:74` / `:565` は自分で確認):

  - monitor の Brier の窓が封印の前日で止まる
  - GUI の的中表示が空になる

  今回の窓の目的は次の世代の候補の確証の証拠を守ることで、本番モデルの凍結 (F3 の封印の目的) とは違う
- **研究の経路だけに効く関所** `scripts/research_window.py` を新設した (`config.RESERVED_FROM` / `config.FRESH_FROM`)。期間は 4 つ:
  development (〜2024) / consumed (2025〜2026-09-13) / reserved (2026-09-14〜FRESH_FROM の前日) / fresh (FRESH_FROM〜)。
  読み込みは目的 (purpose) を必ず渡す:
  - `development`: development だけ
  - `reproduce_consumed`: development と consumed。凍結済みの runner (Group A / C′ / D) の再現だけで、`reproduces` は
    `REPRODUCIBLE_PURPOSES` (主検定を実行した A / C′ の runner の、実行済みの run_index 1 の目的の文字列) の **完全一致** に限る。

  - `primary_after_unlock`: 開封の手順が無いので今は常に止まる。最初の候補の事前登録と一緒に実装する

  reserved はどの目的でも止まる。FRESH_FROM が未確定の間は 2026-09-14 以降をすべて reserved として扱う (fail-closed)。どの期間にも

  テストで確かめる (例外は凍結済みの runner 4 本の完全一致の一覧)。**次の候補の runner・探索のファイルは、この網に入る名前
  (`scripts/<候補>_explore.py` / `scripts/<候補>_run.py` など) で作る**

## 8. 本番の監視と研究の証拠の境界 (2026-10-06 追補、外部の指示者の決定)

> Production monitoring of the already-deployed model does not constitute opening of the research lockbox, provided sealed-window outcomes
> are not joined to candidate features/scores or used to modify candidate specifications.

- 許すこと (本番モデルの運用の監視): 稼働の確認、既存の本番の KPI (Brier 等)、的中の表示、障害の検知
- 研究の側で fresh の期間について禁じること:
  - 候補の S と勝敗を結合する
  - 候補の特徴ごとの成績、部分集団ごとの勝率・回収率、馬ごとの結果の分析
  - 「最近こういう馬が勝っている」を根拠に仕様を変える
  - 本番の監視の数字を候補の設計の根拠として引用する
- つまり production observation ≠ research evidence
- **ai-builder** (別プロジェクト、本番 DB を使う) は本番のシステムとして扱う。その出力・学習の結果を、候補の設計の根拠にしない
- 人が fresh の結果を目にする経路は避けられない (日次の答え合わせの CSV・公開の予想 HTML・Discord の通知・GUI・ai-builder・会話の記憶の
  ファイル)。禁止するのは目にすることではなく、それを候補の特徴・S と **結合** したり、仕様の根拠として **引用** したりすること

## 9. 間の期間 (2026-09-14 〜 FRESH_FROM の前日) = `RESERVED_UNTOUCHED` (2026-10-06 追補、外部の指示者の決定)

- 新しい窓には **含めない** (永久)。A″ の学習・探索・検出力・主検定・金額の試験のどれにも使わず、新しい確証の証拠とも呼ばず、
  研究の目的で結果を開かない。「この 3 週を足せば件数が足りる」という使い方もしない
- 理由: 窓の規則は 2026-10-06 に初めて固定された。9-14 に遡って窓に入れると、見ていなくても「窓の境界を後から選べる」余地が残る。
  データを捨てるのではなく、設計の変更の前後を隔てる緩衝
- 従来の `CONFIRM_FROM = 20260914` (F3 の確認窓) の定義は残すが、研究の経路では reserved として扱う
- **2026-10-06 改訂 (外部の指示者の決定、A″ の事前登録より前): 履歴としてだけの読みの例外**。上の「永久に使わない」は、次のとおり
  「対象としては永久に使わない」(意味は RESERVED_UNTOUCHED_AS_TARGET) と読む。状態名は変えない:

  > reserved 期間は、研究の対象・学習・検証・検出力・診断・金額の試験には永久に使用しない。ただし、FRESH_FROM 以降の対象について、
  > 対象より前に確定していた履歴を、事前に固定した特徴の作り手 (feature extractor) が PIT の特徴を作るために機械的に読むことは許可する。

  - 禁止: reserved のレース自身を予測の対象にする / reserved の勝敗でモデルを選ぶ / reserved で β・回収率・相関・部分集団の分析をする /
    reserved を学習や検出力の計算に足す / 「9 月の馬はこうだった」等を仕様の変更の根拠にする
  - 許可: 2026-10-10 以降の対象の馬について、365 日の過去走として 2026-09 等の走を使う / その履歴を凍結済みの特徴のコードが自動的に評価値へ変える
  - consumed (2025〜2026-09-13) の走も、fresh の対象の履歴としては同じ条件で読める
  - **fresh の期間の中の過去走も同じ原則**: たとえば 2027 年の fresh の対象の 365 日の履歴に、2026-10-10 以降の fresh のレースの結果が入る。
    これは開封のときに、凍結済みのコードが時系列の順に特徴を作るときだけ許す (history_date < target_date)。蓄積の間にそれらの結果を開いて
    特徴を診断することはしない
  - **コードでの強制** (`scripts.research_window.check_history_for_fresh_targets`): 次をすべて満たすときだけ通す。
    対象がすべて fresh / 履歴の窓は [最初の対象日 − 参照日数, 最後の対象日 − 1 日] (期間の粗い上界) / 参照日数は事前に固定した値
    (`HISTORY_LOOKBACK_DAYS`、今は 365 だけ、整数) / 履歴の列は呼び出し側が「表.列」で渡し、市場の表 (払戻・オッズ・票数・WIN5) と
    オッズ・払戻・人気・票数の列を含めない (`data/schema.sql` の全列に対する照合をテストで行う)。さらに、**主検定の開封の中からだけ**
    呼ぶ (開封の手順 = `primary_after_unlock` がまだ無いので、今は条件を確かめた後に常に止まる)
  - **開封の手順と特徴の作り手を実装するときの要件** (最初の候補の事前登録に書く。今はコードで強制していない): 対象ごとの
    history_date < target_date (上の窓は期間の粗い上界で、10/10 の対象に 10/11〜 の fresh の結果が入りうるので、特徴の作り手が対象ごとに
    切り、単体テストで強制する) / 生の履歴の結果を呼び出し元に返さず、派生した特徴と来歴・digest だけを返す / reserved を単独で問い合わせる
    API にしない / 監査ログに残す / 候補の固定の allow-list (表.列) / 開封の記録 (錠・開始の印) を必須の引数にする
