# F3 封印判定 事前登録 (2026-09-14 作成 / 封印開始 2026-10-01 の前に確定)

この文書は **封印が始まる前に判定の条件を全部決めておく** ためのもの。

## なぜ 12 月ではなく今なのか

当初の手順では「判定の直前 (12 月) に仮説と基準を書き出して commit する」と
していた。これは事前登録として成立しない。10〜12 月のあいだ、ユーザは毎週
予想ページと JRA の結果を見る。**人間の目はコードで封印できない**。
10 週間ぶんの感触を得たあとに基準を決めれば、無意識にでも「その基準なら
良い結果が出る」側を選べてしまう。

コードの門 (`config.guard_analysis_window`) は「うっかり集計してしまう」事故を
防ぐレールであって、封印そのものではない。**封印の実体はこの事前登録**。

## 1. 何を測るか (母集団の定義)

| 項目 | 決めた値 |
|---|---|
| 対象 | JRA 中央 (track_code 01-10) の平地・障害を問わない全レース |
| 賭け方 | 単勝 100 円、◎ (最上位) 1 頭のみ |
| 対象レースの条件 | 確定着順があり、払戻行が存在し、発走 10 分前時点の市場情報がある (`--require-market`) |
| 期間 | 2026-10-01 〜 封印窓が下記のレース数に達した日まで |
| 主指標 | 単勝フラット回収率 (賭け金合計に対する払戻合計) |
| 副指標 | mining 特徴を除いた ablation 版の同回収率 (F3 設計制約 (2)) |

**「800 レース」の単位**: 上記の条件を満たして **実際に賭けが成立したレース数**
(母数ではなく bets)。`data/backtest/*_independent_roi_*.json` の `bets` に相当。

## 2. どう計算するか (事後に選べないよう先に固定)

- 信頼区間: **パーセンタイル・ブートストラップ**、両側 95%、B = 10,000、
  リサンプル単位 = **レース** (同一レース内の相関を壊さないため)、seed = 20261001
- 主指標と副指標の 2 つを見るので、**ボンフェローニ補正** をかけ
  各検定は両側 99% (= 片側 0.5%) で判断する
- 集計コマンド (この 1 行だけを 1 回実行する):

```
.venv64\Scripts\python.exe -m scripts.verify_roi_independent --from 20261001 --to <到達日> --require-market --allow-sealed --save
```

## 3. 判定の基準

| 結果 | 判定 |
|---|---|
| 回収率の **下限 > 100%** | 実弾候補に昇格 (それでも少額から) |
| 回収率の **上限 < 100%** | F3 を棄却。封印窓は次の仮説の開発窓に転用 |
| 上記のどちらでもない | **判定不能** (下記 5 の扱いに従う) |

## 4. 検出力 — この判定で何が言えて何が言えないか

live の ◎ 実測 (629 レース) から、1 レースあたりの払戻のばらつきは **SD = 2.79**。
ここから、判定に必要な観測値と、真の回収率別の「判定できる確率」:

| レース数 | 「儲かる」と言うのに必要な観測回収率 |
|---|---|
| 800 | **119% 以上** |
| 1,600 | 114% 以上 |
| 3,200 | 110% 以上 |
| 6,400 | 107% 以上 |

| 真の回収率 | 800 で判定できる確率 | 1,600 で判定できる確率 |
|---|---|---|
| 100% | 2% | 2% |
| 110% | **17%** | 30% |
| 120% | 53% | 82% |
| 130% | 86% | 99% |
| 140% | 98% | 100% |

**つまり 800 レースは「真の回収率が 130% 級」でないと検出できないサイズ**。
JRA の控除率は 20〜30% で、これを突き抜けて 130% を安定して出すモデルは
公開文献に存在しない (`docs/RESEARCH_AI_PREDICTORS_2026.md`)。
現実的にありうる 110〜120% のエッジなら、**判定は 47〜83% の確率で
「分からない」に終わる**。

一方、**棄却側には十分な力がある**。観測が 80% を下回れば上限が 100% を
割るので「エッジは無い」と言い切れる。この検定は最初から非対称で、
「エッジが無いことを確かめる」ためのものだと理解しておく。

これを先に書いておかないと、12 月に「下限 98%、惜しいので継続」という
事後解釈が必ず起きる。

## 5. 判定不能だったときにどうするか (先に決めておく)

**→ ユーザ決定待ち (2026-09-30 まで)**。次のいずれかを選んで、選んだ結果を
この文書に追記してから封印期間に入る。

- (A) **1,600 レースまで延長して、そこで最終判定** (2027 年 3 月頃)。
  判定は延長後の 1 回のみ。800 時点では数字を見ない。
- (B) **800 で打ち切り、判定不能なら F3 を棄却**扱いにする。
  時間を確定させる代わりに、真に 110〜120% のエッジがあっても捨てる。
- (C) **800 時点では回収率を見ず、レース数だけ数えて 1,600 まで自動延長**し、
  途中で判定するかどうかも見ずに決める。

いずれを選んでも「判定は一度だけ」は変えない。

封印中に 1 バイトでも変われば `scripts/auto_predict.py` が生成を中止して
Discord に通知する。判定時にこれらが一致していなければ、封印窓には複数の
モデルの予想が混ざっているので、**その時点で判定は成立しない**。

## 7. 判定の手順

1. 封印窓のレース数だけを数える (成績は見ない)。
2. `config.SEALED_ARTIFACTS` と現物が一致していることを確認する。
3. **封印したまま** 上記 2 のコマンドを `--allow-sealed` で **1 回だけ** 実行する。
   (先に封印を解くと監査ログが残らず、何回試したか分からなくなる)
4. 結果 JSON を commit する。
5. `data/runtime/sealed_access_log.jsonl` を確認する。
   **この文書に書いたコマンド 1 行ぶんの記録しか無いこと**を確かめる。
   それ以外の記録があれば、その判定は「一発勝負」として扱えない。
6. `config.SEALED_JUDGMENT_DONE = True` にして封印解除。

## 8. この判定でも防げないこと (正直に書いておく)

- ユーザが毎週予想ページと JRA の結果を見ることは止められない。
  この文書を先に固定することでしか対処できない。
- 外部リポジトリ `傾向収集/` の週次タスクが `keiba.db` の確定着順を読んでいる。
  別の仮説 (傾向推奨) の評価だが、封印窓の結果が週次で人の目に入る。
  **本リポジトリでは塞げない**。許容するか、その集計を 09/30 で切るかを
  決める必要がある (→ ユーザ決定待ち)。
- 10〜12 月はモデルの劣化監視 (成績側) が凍結される。入力側の監視
  (mining 供給・オッズ取得・出走馬取り込み) は継続するので、
  「壊れた入力のまま 3 ヶ月走る」事故は検知できる。
